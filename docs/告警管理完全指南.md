## 1. 告警系统是干什么的？

**专业术语：** 告警系统（Alerting System）是监控体系的"最后一公里"，负责将 Prometheus 等监控系统采集到的指标异常，通过规则判定、状态管理、聚合去重、路由分发，最终以消息形式送达运维人员。

**大白话：** 你的服务器 CPU 超过 90% 了、磁盘快满了、服务挂了——监控系统发现了这些"不对劲"，告警系统负责判断"这到底算不算问题"、"要不要通知人"、"通知谁"、"怎么通知（微信/邮件/钉钉）"、"多久再提醒一次"。

**核心能力：**
| 能力 | 说明 |
|------|------|
| 规则评估 | 定期执行 PromQL 查询，判断指标是否超过阈值 |
| 状态管理 | 追踪每个告警实例从发现→触发→恢复的全生命周期 |
| 聚合分组 | 将相似的告警合并为一组，避免告警轰炸 |
| 静默抑制 | 在维护窗口期不发送通知，或用高优先级告警压制低优先级 |
| 通知路由 | 根据告警标签，将不同告警发送到不同的通道和团队 |
| 重复通知 | 告警未恢复时，按设定的间隔反复提醒 |
| 恢复通知 | 告警恢复时，发送"已恢复"通知 |

### 2.2 通俗类比

想象你是工厂的**值班班长**：

| 概念 | 类比 | 说明 |
|------|------|------|
| **告警规则 (AlertRule)** | 操作规范手册 | "如果 3 号流水线温度 > 80°C，持续 5 分钟，就算故障" |
| **告警实例 (AlertInstance)** | 当前异常记录 | "刚才 3 号流水线温度 92°C，已持续 7 分钟" |
| **告警分组 (AlertGroup)** | 把同类问题放一个文件夹 | "今天所有温度超标的记录放一起管理" |
| **通知路由 (AlertRoute)** | 值班表 + 上报流程 | "温度问题 → 通知张三 → 如果没解决再通知李四" |
| **通知通道 (NotificationChannel)** | 对讲机 / 电话 / 短信 | "用企业微信通知"还是"发邮件" |
| **通知日志 (AlertNotifyLog)** | 通话记录 | "23:15 已通知张三，他说马上去看" |
| **静默 (Silence)** | "暂时别烦我" | "这个机器在维护窗口期，不通知" |
| **抑制 (Inhibit)** | "更紧急的事优先" | "服务器都宕机了，就别发磁盘告警了" |

## 3. 系统架构与数据流

### 3.1 完整流水线

```
                  ┌──────────────────┐
                  │   Prometheus     │
                  │   (指标存储)      │
                  └────────┬─────────┘
                           │ PromQL 查询
                           ▼
┌──────────────────────────────────────────────┐
│               Evaluator (评估器)               │
│  · 每 15 秒一轮 tick                          │
│  · 遍历所有启用的规则 × 数据源                  │
│  · 执行 PromQL，比对阈值                       │
│  · 产出 Sample 流 (Active=true/false)         │
└────────────────────┬─────────────────────────┘
                     │ EmitSample()
                     ▼
┌──────────────────────────────────────────────┐
│            Dispatcher (调度器)                 │
│                                              │
│  ┌─────────────┐     ┌──────────────────┐    │
│  │ absorb()    │────▶│    flush()        │    │
│  │ 接收 Sample  │     │  每 500ms 批量    │    │
│  │ 更新内存状态  │     │  写 DB + 状态机   │    │
│  └─────────────┘     └────────┬─────────┘    │
│                               │               │
│  ┌────────────────────────────┘               │
│  │                                             │
│  ▼                                             │
│  ┌──────────────────────────────────────┐      │
│  │        dispatchPending()              │      │
│  │  每 1 秒：查到期分组 → 发通知 → 更新   │      │
│  └──────────────┬───────────────────────┘      │
└─────────────────┼──────────────────────────────┘
                  │ SendGroup() / SendResolvedGroup()
                  ▼
┌──────────────────────────────────────────────┐
│              Notifier (通知器)                 │
│  · 合并路由+规则通道                           │
│  · 模板渲染 (simple/table/card/自定义)         │
│  · 限流检查                                   │
│  · 调用通道实现 (微信/邮件/钉钉/飞书/webhook)  │
│  · 写 AlertNotifyLog                          │
└──────────────────────────────────────────────┘
```

### 3.2 三个独立循环

| 循环 | 周期 | 职责 |
|------|------|------|
| **scheduleLoop** | 全局 15 秒（可按规则调整） | 评估 PromQL，产出 Sample |
| **consumeLoop** | 500ms flush 一次 | 吸收 Sample，驱动状态机，写 DB |
| **dispatchLoop** | 1 秒一次 | 查到期分组，发通知 |

三者通过 channel 解耦，互不阻塞。

## 4. 告警规则（AlertRule）详解

### 4.1 规则是什么？

**专业术语：** 告警规则是一段「判定逻辑」的载体，定义了在什么条件下、对哪些数据源、产生什么级别的告警。

**大白话：** 规则就是一份"监控清单"，你告诉系统："帮我盯着这几个机器，如果 CPU > 90% 持续 3 分钟，就标记为严重告警，发到企业微信群里。"

### 4.2 所有字段详解

#### 基本信息

| 字段 | 专业术语 | 大白话 | 默认值 | 示例 |
|------|---------|--------|--------|------|
| `name` | 规则名称 | 给这条规则起个名字 | — | `"生产环境 CPU 使用率过高"` |
| `description` | 规则描述 | 补充说明 | 空 | `"所有物理机 CPU 超过 90% 时告警"` |
| `enabled` | 启用状态 | 打开/关闭这条规则 | `true`（启用） | 勾选 = 开启 |

#### 告警来源 (`source_type`)

| 选项 | 专业术语 | 大白话 |
|------|---------|--------|
| `metric` | 指标复用模式 | 从预定义的指标模板里选一个（比如"CPU 使用率"），系统自动填充 PromQL 和阈值 |
| `custom` | 自定义模式 | 你自己手写 PromQL 查询语句，灵活度最高 |

> **建议：** 新手用 `metric` 模式，熟悉 PromQL 后用 `custom`。

#### PromQL 与阈值

| 字段 | 专业术语 | 大白话 | 说明 |
|------|---------|--------|------|
| `expr` | PromQL 表达式 | 你写的查询语句 | `metric` 模式自动生成，`custom` 模式手写。如 `node_load1 > 20` |
| `threshold` | 阈值 | 触发告警的临界值 | 比如 90（表示 90%） |
| `threshold_type` | 比较方式 | 大于/小于/等于 | `greater`(>) / `greater_equal`(>=) / `less`(<) / `less_equal`(<=) / `equal`(=) / `not_equal`(!=) |
| `has_threshold` | 覆盖阈值 | 是否用自己的阈值覆盖指标模板的 | `metric` 模式下有用，勾选后用自己的阈值 |

#### 告警级别 (`severity`)

| 值 | 专业术语 | 大白话 | 前端颜色 |
|----|---------|--------|---------|
| `critical` | 严重 | 系统挂了，马上起来看 | 红色 |
| `warning` | 警告 | 快出问题了，关注一下 | 橙色 |
| `info` | 提醒 | 知道就行 | 蓝色 |

#### 时间参数

| 字段 | 专业术语 | 大白话 | 默认值 | 示例 |
|------|---------|--------|--------|------|
| `for_duration` | 持续等待时间 | 指标超标后，**等多久**还没恢复才算真告警 | 0（立即触发） | `5m` = 等 5 分钟 |
| `keep_firing_for` | 持续保留时间 | 指标恢复后，**继续维持告警状态多久**再标记恢复 | 0（立即恢复） | `3m` = 恢复后继续显示 3 分钟 |
| `eval_interval_sec` | 评估间隔 | 多久查一次 Prometheus | 0（用全局 15 秒） | `60` = 每 60 秒查一次 |

> **`for_duration` 案例：** 设 `for_duration=5m`，CPU 到了 95%，系统不会立刻告警，而是等 5 分钟。如果 5 分钟到了还超阈值 → 触发告警。如果 3 分钟时降回 50% → 不算告警（这叫「毛刺过滤」）。
>
> **`keep_firing_for` 案例：** 设 `keep_firing_for=3m`，CPU 恢复了，但告警仍然显示 3 分钟才标记为"已恢复"。用于避免告警在阈值边界反复横跳（这叫「闪烁抑制」）。

#### 通知相关

| 字段 | 专业术语 | 大白话 | 优先级 |
|------|---------|--------|--------|
| `repeat_interval` | 重复间隔 | 告警一直没好，**隔多久再发一次通知** | 规则 > 路由 > 默认 4h |
| `max_send_count` | 最大发送次数 | 同一个告警最多通知几次 | 规则 > 路由 > 0（不限） |
| `route_id` | 指定路由 | 这条告警走哪个通知路由 | 非空时强制走指定路由 |
| `notify_channel_ids` | 直发通道 | 不走路由，直接发到这些通道 | 与 route_id 互斥 |

> **`repeat_interval` vs `group_interval` vs `group_wait`**：这三个最容易混，详见第 8.4 节。

#### 数据源选择

| 字段 | 专业术语 | 大白话 |
|------|---------|--------|
| `datasource_ids` | 数据源 ID 列表 | 选中几个 Prometheus 数据源，对它们执行 PromQL |
| `datasource_selector` | 数据源选择器 | 用标签批量选数据源，如 `{"project_name":"prod"}` |

> 二者二选一。`datasource_ids` 适合少量数据源手动选，`datasource_selector` 适合大批量数据源按标签自动匹配。

#### 附加信息

| 字段 | 专业术语 | 大白话 |
|------|---------|--------|
| `labels_json` | 标签 | 给这条告警打标签（如 `{"team":"infra","env":"prod"}`），用于路由匹配和分组 |
| `annotations_json` | 注释 | 告警消息的补充信息，支持模板变量 `{{ $value }}`、`{{ $threshold }}`、`{{ .instance }}` |
| `cause` | 可能原因 | 告警触发后，通知里会附上这段文字 |

### 4.3 配置案例

**案例：监控生产环境所有节点的磁盘使用率**

```json
{
  "name": "生产环境磁盘使用率告警",
  "description": "根分区磁盘使用率超过 85% 时触发",
  "source_type": "custom",
  "expr": "(node_filesystem_size_bytes{mountpoint=\"/\"} - node_filesystem_avail_bytes{mountpoint=\"/\"}) / node_filesystem_size_bytes{mountpoint=\"/\"} * 100",
  "threshold": 85,
  "threshold_type": "greater",
  "has_threshold": true,
  "severity": "critical",
  "for_duration": "5m",
  "keep_firing_for": "3m",
  "eval_interval_sec": 60,
  "repeat_interval": "2h",
  "max_send_count": 10,
  "datasource_ids": [1, 2, 3],
  "labels_json": "{\"team\":\"infra\",\"env\":\"prod\"}",
  "annotations_json": "{\"summary\":\"节点 {{ .instance }} 磁盘使用率 {{ $value }}\"}",
  "cause": "日志文件未清理、数据增长过快、磁盘未扩容",
  "impact": "可能影响服务写入，严重时服务只读",
  "notify_channel_ids": [1, 2],
  "enabled": true
}
```

## 5. 通知路由（AlertRoute）详解

### 5.1 路由是什么？

**专业术语：** 通知路由是一棵「匹配树」，告警按标签从上到下匹配，匹配到哪个节点就按哪个节点的配置发送通知。支持父子层级，子节点继承父节点未设置的参数。

**大白话：** 路由就是一张"分流表"。比如"严重级别的告警发给核心团队微信群"、"一般告警发给值班群"、"磁盘告警发给存储团队飞书群"。路由可以嵌套：先按严重级别分流，严重告警里再按业务线细分。

### 5.2 路由树结构

```
默认路由 (根路由, 兜底)
├── 匹配条件: 无 (所有告警都匹配)
├── group_wait: 30s, repeat_interval: 4h
├── 通道: 企业微信
│
├── [子路由 A] 严重告警路由
│   ├── 匹配条件: severity = critical
│   ├── 通道: 企业微信核心群
│   ├── send_resolved: true
│   │
│   ├── [子路由 A-1] 基础设施严重告警
│   │   ├── 匹配条件: team = infra
│   │   ├── 通道: 基础设施紧急群
│   │
│   └── [子路由 A-2] 应用严重告警
│       ├── 匹配条件: team = app
│       ├── 通道: 应用核心群
│
└── [子路由 B] 提醒级别路由
    ├── 匹配条件: severity = info
    ├── 通道: 邮件
    └── repeat_interval: 24h (覆盖父路由)
```

**匹配规则：**
1. 从根路由开始，逐层向下匹配
2. 告警标签必须匹配节点的 `matchers_json` 条件
3. 匹配到叶子节点后，使用该节点 + 所有祖先节点的参数（子节点覆盖父节点）
4. 如果父节点勾选了 `continue`，即使匹配了父节点，还会继续检查同级兄弟节点

### 5.3 所有字段详解

| 字段 | 专业术语 | 大白话 | 默认值 |
|------|---------|--------|--------|
| `name` | 路由名称 | 名字 | — |
| `parent_id` | 父路由 | 挂在哪个节点下面 | null（根路由） |
| `matchers_json` | 匹配条件 | 什么样的告警走这里 | 空（匹配全部） |
| `continue` | 继续匹配 | 匹配后还要不要看下一个同级节点 | `false` |
| `group_by_json` | 分组标签 | 按什么标签把告警归到一组 | `["alertname"]` |
| `group_wait` | 首次等待 | 新组创建后等多久再发首次通知 | `30s` |
| `group_interval` | 分组间隔 | 组内新告警追加时，多久发一次 | `5m` |
| `repeat_interval` | 重复间隔 | 告警持续未恢复，隔多久再通知 | `4h` |
| `throttle_window` | 限流窗口 | 相同内容的消息多久内不重复发 | 空 = 用 repeat_interval |
| `send_resolved` | 恢复通知 | 告警恢复时要不要发通知 | `false`（不发） |
| `max_send_count` | 最大发送次数 | 最多通知几次 | 0（不限） |
| `notify_channel_ids` | 通知通道 | 发到哪个通道 | 空（需配置） |
| `priority` | 优先级 | 同级节点谁先匹配 | 0（值越大越优先） |
| `enabled` | 启用 | 开/关 | `true` |

### 5.4 分组标签 (`group_by`) 详解

**这是整个告警系统最重要的概念之一。**

**专业术语：** `group_by` 指定一组标签 key，系统将具有相同标签值的告警归入同一个 AlertGroup（告警分组），作为通知的最小调度单元。

**大白话：** 你告诉系统"把什么看作同一件事"。比如按 `["alertname","instance"]` 分组，那"节点 A 的 CPU 告警"和"节点 B 的 CPU 告警"就是两件事，各自独立触发/恢复/通知。如果只按 `["alertname"]`，那所有节点的 CPU 告警都算"同一件事"，要全部恢复才算恢复。

**分组粒度的影响：**

| group_by 设置 | 效果 | 适用场景 |
|--------------|------|---------|
| `["alertname"]` | 按规则名分组，所有节点合并 | 想一条通知看所有异常节点 |
| `["alertname","instance"]` | 按规则名+节点分组，各节点独立 | 每个节点触发/恢复独立通知 |
| `["alertname","datasource_id"]` | 按规则名+数据源分组 | 多集群场景，每个集群独立 |
| `["alertname","severity"]` | 按规则名+级别分组 | 同一规则下按级别分开通知 |
| `["alertname","datasource_id","instance"]` | 最细粒度 | 每个节点每个规则完全独立 |

> **⚠️ 分组的实际影响：**
> - 组内**任一实例**触发 → 整组发**触发通知**
> - 组内**全部实例**恢复 → 整组发**恢复通知**（需开启 send_resolved）
> - 粒度越粗，恢复通知越少（要等所有节点都恢复）
> - 粒度越细，通知越多（每个节点独立触发和恢复）

### 5.5 三个时间参数的关系

这是告警系统最容易混淆的三个概念，放在一起讲：

| 参数 | 触发时机 | 作用 |
|------|---------|------|
| **group_wait** | 分组刚创建时 | 等一会儿再发首次通知，在这段时间内可能还有同类告警进来，可以聚合一起发 |
| **group_interval** | 组内已有告警，又来了新告警时 | 新告警追加时，控制通知频率 |
| **repeat_interval** | 组已通知过，状态没变时 | 告警持续不恢复，隔多久再提醒一次 |

**时间线示例：**

```
group_wait=30s, group_interval=5m, repeat_interval=1h

时间轴：
00:00  节点 A 磁盘超阈值 → 创建新组 → 开始 group_wait 30s 倒计时
00:15  节点 B 磁盘超阈值 → 加入同一组（聚合）
00:30  group_wait 到期 → 发首次通知（包含 A+B）
       ─── 组状态变为 notified ───
00:45  节点 C 磁盘超阈值 → 加入组 → 触发 group_interval 检查
       （上次通知在 00:30，距现在 0.25h < 5m → 不会立即发）
00:30 + 5m = 05:30  group_interval 到期 → 发第 2 次通知（含 A+B+C）
10:30  上次通知 05:30，repeat_interval=1h → 已过 5h → 到下一整点 06:30 发第 3 次
       但注意：repeat_interval 是从上次通知时间 + 1h，所以是 05:30+1h=06:30
06:30  发第 3 次通知（告警仍存在，重复通知）
...
一直重复直到告警恢复或达到 max_send_count
```

### 5.6 max_send_count + 每日重置

**专业术语：** `max_send_count` 是告警组允许发送的通知次数上限。达到上限后不再发送，但每天零点自动重置归零。

**大白话：** 同一个告警别没完没了。设置 `max_send_count=5`，半夜 3 点开始触发，到早上 8 点最多发 5 条。第二天继续。

## 7. 告警生命周期：pending → firing → resolved

### 7.1 状态转换图

```
                         for_duration 到期
                    ┌──────────────────────┐
                    │                      │
                    ▼                      │
   ┌─────────┐    ┌─────────┐    ┌──────────┐
   │ 不存在   │───▶│ pending │───▶│ firing   │
   └─────────┘    └─────────┘    └────┬─────┘
         ▲                            │
         │    keep_firing_for 到期     │
         │    ┌───────────────────────┘
         │    │
         │    ▼
         │  ┌──────────┐
         └──│ resolved │
            └──────────┘
```

### 7.2 三个阶段详解

#### pending（待确认）

| 项目 | 说明 |
|------|------|
| **怎么进入** | PromQL 查询结果首次超过阈值 |
| **状态含义** | "指标确实超了，但在等 for_duration 确认不是毛刺" |
| **能干嘛** | 前端可以看到，但**不会触发通知**、**不会创建告警组** |
| **怎么离开** | ① 持续超阈值直到 for_duration 到期 → 转为 firing |
| | ② 在 for_duration 内恢复正常 → 直接从内存删除（不留痕迹）|

> **大白话：** pending 就像一个"怀疑名单"。指标超了先记在小本子上，等够时间确认是真的异常才真正拉警报。如果中途恢复了，就当没发生过。

#### firing（触发中）

| 项目 | 说明 |
|------|------|
| **怎么进入** | pending 持续超 threshold 超过 for_duration |
| **状态含义** | "确认异常，需要通知人" |
| **能干嘛** | 触发通知派发、创建告警组、写入告警历史 |
| **怎么离开** | ① 指标恢复正常且 keep_firing_for 到期 → 转为 resolved |
| | ② 指标依然异常 → 保持 firing（按 repeat_interval 重复通知）|

#### resolved（已恢复）

| 项目 | 说明 |
|------|------|
| **怎么进入** | 指标恢复且 keep_firing_for 到期 |
| **状态含义** | "问题已经解决了" |
| **能干嘛** | 触发恢复通知（如果开启 send_resolved）、记录历史 |
| **怎么清理** | resolved 保留一轮 flush 后自动从活跃列表删除 |

### 7.3 边界情况

| 场景 | 处理方式 |
|------|---------|
| 规则被删除 | 关联实例强制 resolved |
| 数据源不可用 | circuit breaker 打开，跳过评估，实例保持原状态 |
| 数据源永久下线 | 规则判定为 `ruleDead`，实例强制 resolved |
| 评估器重启 | 从 DB 恢复 pending/firing 实例到内存，保持状态连续 |

## 8. 通知派发逻辑：一条告警如何变成一条微信消息

### 8.1 完整链路

```
firing 实例
    │
    ▼
applyRouting()
    │
    ├── 匹配路由树（按告警标签）
    ├── 计算 group_by → 得到 group_key
    ├── 查/创 AlertGroup
    │   ├── 新组 → next_notify_at = now + group_wait
    │   └── 已有组 → alert_count++, 调整 next_notify_at
    │
    ▼
dispatchPending() [每 1 秒执行]
    │
    ├── 日期变了？→ 重置所有 send_count = 0
    ├── 查 DB: next_notify_at <= now 且 state IN (pending, notified)
    │
    ├── 对每个到期分组：
    │   │
    │   ├── 拉取活跃实例（pending/firing）
    │   │
    │   ├── 无活跃实例？→ 恢复通知流程（见第 9 节）
    │   │
    │   ├── send_count >= max_send_count？
    │   │   └── 写日志"已达上限" → 按 repeat_interval 推后 → 跳过
    │   │
    │   ├── 过滤静默/抑制实例
    │   │   └── 全部被屏蔽？→ 按 repeat_interval 推后 → 跳过
    │   │
    │   ├── 调用 Notifier.SendGroup()
    │   │   │
    │   │   ├── 合并通道：路由通道 ∪ 规则通道
    │   │   ├── 检查通道是否启用
    │   │   ├── 计算限流窗口
    │   │   ├── 对每个通道：
    │   │   │   ├── 渲染模板
    │   │   │   ├── 限流检查（相同 hash 在窗口内？）
    │   │   │   ├── 实际发送（HTTP 请求）
    │   │   │   └── 写通知日志 (success/failed/throttled)
    │   │   └── 更新 alert_histories 的 notify 字段
    │   │
    │   └── 更新 AlertGroup：
    │       ├── send_count++
    │       ├── state = notified
    │       ├── last_notified_at = now
    │       └── next_notify_at = now + repeat_interval
    │
    ▼
    下一次 dispatchLoop tick → 重复
```

### 8.2 通道合并规则

**专业术语：** 路由上的通道和规则上的通道取**并集**。

**大白话：** 如果路由配置了"企业微信"，规则配置了"邮件"，那最终会发到两个地方。如果两边配了同一个通道，也只发一次。

**为什么不覆盖？** 这样你可以：
- 路由上配一个通用的"值班群"
- 规则上配一个专用的"业务群"
- 两边都收到通知

### 8.3 限流机制（Throttle）

**专业术语：** Throttle 是通过内容哈希去重，在限流窗口内相同内容的告警消息只发一次。

**大白话：** 如果 5 秒前刚发了一条"CPU 过高"的通知，内容和现在要发的一模一样，那这条就不发了，避免刷屏。

**限流窗口优先级：** 路由 `throttle_window` > 规则 `repeat_interval` > 路由 `repeat_interval` > 默认 30s

### 8.4 三个时间参数的选择指南

| 你想实现的效果 | group_wait | group_interval | repeat_interval |
|--------------|-----------|---------------|----------------|
| 告警立即通知 | 0s | — | — |
| 等一等聚合更多告警再通知 | 30s~5m | — | — |
| 告警期间来新实例别太吵 | — | 5m~30m | — |
| 持续未恢复每小时提醒一次 | — | — | 1h |
| 每天上班提醒一次 | — | — | 8h~24h |
| 只在凌晨发一次，别半夜吵人 | — | — | 配合 max_send_count |

### 8.5 通知失败处理

| 情况 | 行为 | send_count 累加？ | next_notify_at |
|------|------|-----------------|----------------|
| 发送成功 | 更新状态 | ✅ 是 | now + repeat_interval |
| 无可用通道 (ErrNoChannels) | 写日志，跳过 | ❌ 否 | now + repeat_interval |
| 全部通道禁用 | 写日志，跳过 | ❌ 否 | now + repeat_interval |
| 全部被静默/抑制 | 按 repeat 重排 | ❌ 否 | now + repeat_interval |
| 发送失败（网络错误等） | 写日志，跳过 | ❌ 否 | now + repeat_interval |
| 达到 max_send_count | 写日志"已达上限" | 已是最多次 | now + repeat_interval（避免每 tick 刷日志）|

> 关键设计理念：**只要没成功发送，就不算次数，也不标记为 notified**。这样通道配置补全后，下一轮调度能自动恢复发送。

## 9. 恢复通知逻辑

### 9.1 触发条件

当告警组内**所有活跃实例**都转为 resolved 时，系统才会发送恢复通知。

```
组内有 3 个实例（A、B、C 都在 firing）
  │
  ├── A 恢复 → 组内还有 B、C 在 firing → ❌ 不发恢复通知
  ├── B 恢复 → 组内还有 C 在 firing → ❌ 不发恢复通知
  └── C 恢复 → 组内全 resolved → ✅ 发恢复通知
```

### 9.2 完整流程

```
flush()
  │
  ├── 实例状态 firing → resolved
  ├── 收集该实例的 group_key 到 resolvedGroupKeys
  │
  ▼
检查每个 resolvedGroupKeys：
  │
  ├── 组内还有 pending/firing 实例？→ 跳过
  └── 组内无活跃实例？→ 将 AlertGroup.next_notify_at = now
      │
      ▼
  dispatchPending() 下一 tick
      │
      ├── 查到期分组（next_notify_at <= now）
      ├── 查组内实例 → 无活跃
      ├── 查组内 resolved 实例 → 有
      ├── 检查 route.send_resolved = true？→ 发恢复通知
      └── 组状态 → idle
```

### 9.3 为什么说分组粒度很重要？

回到第 5.4 节的例子：

```
group_by = ["alertname"]
  │
  ├── 6 个节点全部在一个组
  └── 只有当全部 6 个都恢复时 → 发 1 条恢复通知

group_by = ["alertname","instance"]
  │
  ├── 6 个节点分在 6 个独立组
  └── 每个节点恢复时 → 各自发 1 条恢复通知（共 6 条）
```

**选择建议：** 如果你希望每个节点独立管理生命周期（各发各的触发和恢复），就把 `instance` 加入 `group_by`。

## 10. 参数优先级链

### 10.1 重复间隔（repeat_interval）

```
规则.repeat_interval     ← 最高优先级
    ↓ (为空时)
路由.repeat_interval     ← 中间优先级
    ↓ (为空时)
默认值 4h                ← 兜底
```

### 10.2 最大发送次数（max_send_count）

```
规则.max_send_count      ← 最高优先级
    ↓ (=0 时)
路由.max_send_count      ← 中间优先级
    ↓ (=0 时)
0（不限次数）            ← 兜底
```

### 10.3 通知通道

```
路由.notify_channel_ids
    ∪                     ← 并集（不是覆盖！）
规则.notify_channel_ids   ← 两者都发
```

### 10.4 限流窗口（throttle_window）

```
路由.throttle_window       ← 最高优先级（显式设置）
    ↓ (为空时)
规则.repeat_interval
    ↓ (为空时)
路由.repeat_interval
    ↓ (为空时)
默认 30s                  ← 兜底
```

### 10.5 评估间隔（eval_interval_sec）

```
规则.eval_interval_sec    ← 规则自定义
    ↓ (=0 时)
全局默认 15 秒            ← 兜底
```

### 10.6 分组标签（group_by）

```
路由.group_by_json         ← 路由配置
    ↓ (为空时)
["alertname"]              ← 兜底
```

### 10.7 规则优先于路由（总原则）

```
规则级参数（如果有）→ 路由级参数（如果有）→ 系统默认值
```

## 11. 配置联动性：规则、路由、通道如何配合工作

### 11.1 三者关系

```
┌──────────────┐      ┌──────────────┐      ┌──────────────────┐
│  告警规则      │      │  通知路由      │      │  通知通道          │
│              │      │              │      │                  │
│  · 定义触发   │──────▶  · 按标签分流  │──────▶  · 微信/邮件/钉钉  │
│  · 定义分组   │      │  · 控制频率    │      │  · 模板渲染        │
│  · 定义级别   │      │  · 决定通道    │      │  · API 调用        │
└──────────────┘      └──────────────┘      └──────────────────┘
```

### 11.2 一条告警的配置之旅

假设有这样的配置：

```
步骤 1: 规则评估
  ┌─────────────────────────────────────────┐
  │ 一条规则: "CPU > 90%, severity=critical" │
  │ labels: {team: "infra", env: "prod"}    │
  │ notify_channel_ids: [1] （企业微信）     │
  └─────────────────────────────────────────┘
              │
              ▼ (告警产生，进入路由匹配)
步骤 2: 路由匹配
  ┌─────────────────────────────────────────┐
  │ 路由树:                                   │
  │ ├─ 根路由 (兜底: 企业微信总群)            │
  │ ├─ severity=critical → 核心群            │
  │ │  └─ team=infra → 基础设施群            │
  │ │     ├─ group_by: [alertname,instance]  │
  │ │     ├─ repeat_interval: 1h             │
  │ │     └─ send_resolved: true             │
  └─────────────────────────────────────────┘
              │
              ▼ (匹配到 "基础设施群" 路由节点)
步骤 3: 参数合并
  ┌─────────────────────────────────────────┐
  │ 最终生效参数:                              │
  │ group_by: [alertname,instance]           │
  │ repeat_interval: 1h (路由)               │
  │ 通道: 路由的[核心群] ∪ 规则的[企业微信]    │
  │ send_resolved: true                      │
  └─────────────────────────────────────────┘
```

### 11.3 标签的联动作用

**标签（labels）是整个告警系统的"粘合剂"：**

| 作用 | 说明 |
|------|------|
| **路由匹配** | 路由的 `matchers_json` 用标签来匹配告警 |
| **分组聚合** | `group_by` 按标签值将告警归到一个组 |
| **静默匹配** | 静默规则的 matchers 也是基于标签 |
| **抑制匹配** | 抑制规则的 source/target matchers 也是基于标签 |
| **消息模板** | 模板中可以引用标签值 `{{ .instance }}` 等 |

> **一条重要的设计原则：** 规则中的 `labels_json` 是告警的"身份证"，影响路由、分组、静默、抑制的一切行为。

## 12. 数据之间的联动关系

### 12.1 表的关联

```
alert_rules
  │
  ├── datasource_ids → data_sources (多对多)
  ├── route_id → alert_routes (可选，指定路由)
  ├── notify_channel_ids → notification_channels (可选，直发通道)
  └── metric_config_id → metric_configs (可选，复用指标)
       │
       ▼
alert_instances
  │
  ├── rule_id → alert_rules
  ├── datasource_id → data_sources
  ├── group_key → alert_groups (告警分组)
  │                │
  │                ├── route_id → alert_routes
  │                └── group_key ← alert_notify_logs (通知日志)
  │
  └── fingerprint ← alert_histories (按 fingerprint 关联历史)
```

### 12.2 关键字段之间的联动

| 配置 A | 影响 | 配置 B | 说明 |
|--------|------|--------|------|
| 规则 `labels_json` | → | 路由 `matchers_json` | 告警带什么标签，决定走哪个路由 |
| 路由 `group_by_json` | → | AlertGroup `group_key` | 分组标签变了，group_key 就变了 |
| group_key 不同 | → | 通知独立 | 不同组各自管自己的触发/恢复/频率 |
| 路由 `notify_channel_ids` | ∪ | 规则 `notify_channel_ids` | 通道合并 |
| 规则 `repeat_interval` | > | 路由 `repeat_interval` | 规则覆盖路由 |
| 规则 `max_send_count` | > | 路由 `max_send_count` | 规则覆盖路由 |
| 路由 `send_resolved` | → | dispatch 发恢复通知 | 关闭就不发恢复通知 |
| 路由 `group_wait` | → | 新组首次通知延迟 | 首次通知时间 |
| AlertGroup `next_notify_at` | → | dispatch 轮询 | 只有到期的组才被调度 |
| 每日 00:00 | → | AlertGroup `send_count=0` | 每天重置发送计数 |

### 12.3 数据流向总结

```
配置层（定义 what）
  rules + routes + channels + silences + inhibits
      │
      ▼
运行层（处理 when/how）
  evaluator → stateManager → dispatcher → notifier
      │
      ▼
数据层（记录 what happened）
  alert_instances + alert_groups + alert_notify_logs + alert_histories
```

## 13. 完整配置案例

### 案例 1: 最简单的告警

**目标：** 监控所有节点 CPU 负载，超过 20 持续 1 分钟就告警，每 4 小时重复通知一次，发到企业微信。

**规则配置：**
```json
{
  "name": "节点负载告警",
  "source_type": "custom",
  "expr": "node_load1",
  "threshold": 20,
  "threshold_type": "greater",
  "for_duration": "1m",
  "datasource_ids": [1],
  "severity": "warning",
  "repeat_interval": "4h",
  "notify_channel_ids": [1],
  "enabled": true
}
```

**路由配置：** 使用默认路由，`notify_channel_ids=[1]`（企业微信）。

### 案例 3: 多级路由分流

**目标：** 严重告警发核心群，一般告警发值班群，磁盘告警因为磁盘管理员要看所以额外发邮件。

**路由树配置：**

根路由（兜底）：
```json
{
  "name": "默认路由",
  "group_wait": "30s",
  "repeat_interval": "4h",
  "notify_channel_ids": [1],
  "send_resolved": false
}
```

子路由 A - 严重告警：
```json
{
  "name": "严重告警路由",
  "parent_id": 1,
  "matchers_json": "[{\"name\":\"severity\",\"op\":\"=\",\"value\":\"critical\"}]",
  "repeat_interval": "1h",
  "send_resolved": true,
  "notify_channel_ids": [2]
}
```

子路由 B - 磁盘告警（额外发邮件）：
```json
{
  "name": "磁盘告警路由",
  "parent_id": 1,
  "matchers_json": "[{\"name\":\"alertname\",\"op\":\"=~\",\"value\":\".*磁盘.*\"}]",
  "notify_channel_ids": [1, 3]
}
```

**效果：**
- 严重告警 → 发到通道 2（核心群），每小时重试
- 磁盘告警 → 同时发到通道 1（值班群）和通道 3（邮件）
- 其他告警 → 发到通道 1（值班群），每 4 小时重复

## 14. 常见问题与排错

### Q1: 告警规则配好了，但一直没有告警？

**排查步骤：**
1. 检查规则是否已启用（`enabled = true`）
2. 检查数据源是否可达：`/api/promai/alert/evaluator/status` 看 `eval_success_count` 是否 > 0
3. 用「测试」功能验证规则，查看 PromQL 返回结果
4. 检查 `for_duration`：如果设置 `for_duration=5m`，需要持续超阈值 5 分钟才会 firing
5. 检查 `datasource_ids` 是否正确

### Q2: 告警触发了，但没有收到通知？

**排查步骤：**
1. 检查通知通道是否已启用：通知通道管理 → 确认通道 `enabled = true`
2. 检查路由是否配置了该通道：路由 → `notify_channel_ids` 是否包含该通道
3. 检查规则是否有直发通道：规则 → `notify_channel_ids`
4. 检查路由的 `send_resolved`：如果是恢复通知没收到，确认已开启
5. 检查 `max_send_count`：是否已达到上限（日志会标注"已达最大发送次数上限"）
6. 查看通知日志：`/api/promai/alert/notify-logs` 看是否有 failed/throttled 记录
7. 查看服务器日志：搜索 `[Dispatch]` 和 `[Notify]` 前缀

### Q3: 恢复通知没收到？

1. 确认路由开启了 `send_resolved = true`
2. 确认分组内**所有**实例都已恢复（部分恢复不会触发）
3. 如果希望每个节点独立恢复通知，把 `instance` 加到 `group_by`

### Q4: 通知发得太频繁/太少了？

| 问题 | 调整参数 |
|------|---------|
| 告警刚触发就想收到 | 缩短 `group_wait` 或设为 `0s` |
| 告警期间来了新实例太吵 | 增大 `group_interval` |
| 持续告警每小时提醒太吵 | 增大 `repeat_interval` |
| 一天只想提醒一次 | 设 `repeat_interval=24h` + `max_send_count=1` |
| 半夜别吵人 | 设 `max_send_count=3`，白天重置后再发 |

### Q5: 怎么理解 group_by 和告警组的对应关系？

直接在 SQLite 中查看：
```sql
-- 查看所有告警组及其包含的标签
SELECT id, group_key, alert_count, state, next_notify_at
FROM alert_groups
ORDER BY id;

-- 查看每个实例所属的组
SELECT id, group_key, state, labels_json
FROM alert_instances
ORDER BY group_key;
```

### Q6: 告警通知里的内容太简短/太详细？

在通知通道的「消息模板」中调整：
- `simple`：最简短紧凑
- `table`：一行一条
- `card`：带图标的详细布局
- `custom`：完全自定义 Go 模板

### Q7: 评估器日志经常出现 "record not found"？

这是正常情况。`state.go:379` 的 `ErrRecordNotFound` 只是 upsert 时检查实例是否存在，不存在就创建，不是错误。

## 附录 A：字段类型速查表

### 时间单位写法

| 单位 | 写法 | 示例 |
|------|------|------|
| 秒 | `s` | `30s` |
| 分 | `m` | `5m` |
| 时 | `h` | `4h` |
| 天 | 不支持 | 用 `24h` |

### 阈值比较符

| 前端显示 | 代码值 | 含义 |
|---------|--------|------|
| > | `greater` / `gt` | 大于 |
| >= | `greater_equal` / `ge` | 大于等于 |
| < | `less` / `lt` | 小于 |
| <= | `less_equal` / `le` | 小于等于 |
| = | `equal` / `eq` | 等于 |
| != | `not_equal` / `ne` | 不等于 |

### 标签匹配操作符

| 操作符 | 含义 | 示例 |
|--------|------|------|
| `=` | 精确等于 | `severity = critical` |
| `!=` | 不等于 | `severity != info` |
| `=~` | 正则匹配 | `alertname =~ .*磁盘.*` |
| `!~` | 正则不匹配 | `instance !~ 192\.168\..*` |
